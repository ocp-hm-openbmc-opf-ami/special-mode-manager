    Allow root to SSH with ValJumper even if already enabled (#2)
    
    If the root user was enabled at the time of jumper assertion, the
    logic would consider the user already configured and not add the
    priv-admin group membership. However, this leads to inconsistency and
    confusion, so now `enableSpecialUser` will consider the password and
    group separately when making changes. Now the expectations are:
    
    1. Root user can *always* SSH after asserting jumper (and setting
       first password on console if needed).
    2. Root user is disabled and removed from priv-admin upon jumper
       de-assertion.

      FM_BMC_VAL_EN at boot.

      SSH. /var/val_jumper_assert_cleanup_required exists.
    
    - Rebooted and disabled gpio-mockup bootargs to simulate deassertion of
      FM_BMC_VAL_EN.
    - Verified features were disabled: could no longer login or SSH.
    
    - Set password via IPMI command, then rebooted and asserted jumper.
      Confirmed that same password was accepted (didn't prompt to set new
      one), but root was also added to priv-admin and could SSH.

    Fix improper password modification
    
    When the root user is configured for manufacturing mode, the password
    hash was being modified via putspent() in a way that left /etc/shadow
    with an invalid line containing "7:::". The proper way to use putspent()
    seems to require writing out all shadow entries at once to avoid this.
    After setting the password at first login, /etc/shadow gets rewritten
    and the invalid entry is discarded, so this bug was possibly harmless.
    
    This commit replaces putspent() with a subprocess call to the passwd
    utility, which is much more likely to avoid such bugs. The File class
    was also not handling locking correctly, but now we can avoid dealing
    with all of that.
    
    Tested:
    - Build without debug-tweaks
    - factory reset BMC and reboot into manufacturing mode.
    - Able to login as root on console and set initial password
    
    Change-Id: Idb7cdc783ceea609a9054fad70f9efff7e1ee26b
    Signed-off-by: Jonathan Doman <jonathan.doman@intel.com>
